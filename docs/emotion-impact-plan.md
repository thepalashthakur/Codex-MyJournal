# Journal sections and emotional context: implementation plan

1. **Preserve the current entry body.** `entries.content` remains the quick writing surface, with its TipTap JSON, revision checked `save_entry` RPC, browser draft, and existing readers. New `entry_sections` are optional ordered companions to an entry. No existing content is rewritten or deleted.
2. **Add owner-scoped relational data.** A migration will add sections, user-owned emotions, one section emotion with optional 1–10 intensity, impact areas, entities, and section associations. Composite foreign keys, unique indexes, checks, RLS, and authenticated grants enforce ownership and shape. Default emotions are copied from a database catalog into each user's library. Configuration deletion preserves referenced history.
3. **Keep writes in services.** Server services validate inputs, resolve the authenticated user via `userDb`, verify parent resources, and perform mutations. Route handlers perform same-origin checks on writes. Section content updates use a revision condition to prevent an older autosave response from replacing a newer one.
4. **Extend the editor progressively.** The primary body editor remains unchanged. A secondary section list lets users add, duplicate, reorder, edit, and remove sections. Emotion and impact pickers support fast inline creation; settings screens manage the full libraries. Only the current entry's sections and the user's small configuration libraries are sent to the editor.
5. **Integrate discovery and portability.** Search adds exact emotion, area, and entity filters. JSON and Markdown exports include sections and emotional context. Existing entries and exports remain interpretable.
6. **Verify in coherent slices.** Add domain and security tests, run lint, typecheck, tests, and production build. Live authenticated flows and migration application require the configured Supabase project and are separate verification gates.
